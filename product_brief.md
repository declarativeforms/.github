# Product Brief: Declarative Forms

## 1. Product Overview

Declarative Forms is a form platform that turns YAML files in a public GitHub repository into live, hosted forms — no account required.

**Core mechanism:** Write a YAML file → push to any public GitHub repo → form is live at `https://app.declarativeforms.com/{owner}/{repo}/{filename}`.

**App URL:** `https://app.declarativeforms.com`

---

## 2. Problem Statement

Modern developer tooling is config-based. Infrastructure, CI pipelines, deployments — all of it is declarative, lives in version control, and can be generated by LLMs. Forms remain the exception.

Every existing form platform forces you through a UI builder. There is no programmatic API for creating forms, no way to commit a form definition to a repository, no diff history, no code review. When you want to generate a form with an AI tool, you have nowhere to put the output.

This gap grows as AI-assisted development tools become the primary way people build products. The people using these tools expect everything to work the way code works — described in text, version-controlled, reviewable, automatable. Forms don't fit that pattern today.

---

## 3. Target Audience

- Developers building internal tools, surveys, onboarding flows, or data collection
- Teams already using Git-based workflows who want forms to follow the same pattern
- AI-assisted builders using tools like Claude Code, Codex, and similar — who generate forms via prompt rather than clicking through a UI
- Indie hackers and small teams who need forms without SaaS overhead or vendor lock-in

---

## 4. Core Value Proposition

**Works with AI tools.** Describe the form in plain language, get YAML back, push to GitHub. No UI interaction required at any step.

**Lives in your repo.** Every change is a commit. You get history, diffs, and code review for free. The form definition is just a file.

**No account required.** A public GitHub repository is sufficient. There is no sign-up gate between writing a YAML file and having a live form.

---

## 5. How It Works

1. Write a YAML file (the filename becomes the form identifier).
2. Push to any public GitHub repository.
3. Form is live at: `https://app.declarativeforms.com/{owner}/{repo}/{form_name}`

**Example:** A file named `rental.yaml` in `github.com/acme/forms` is live at:
```
https://app.declarativeforms.com/acme/forms/rental
```

### Reserved URL query parameters

These parameters are used by the platform and cannot be used for prefill:

| Parameter | Purpose |
|---|---|
| `connection_id` | References a stored OAuth connection |
| `lang` | Overrides the form locale |
| `submission_id` | Tracks a partial or in-progress submission |
| `step` | Resumes a submission at a specific section |

Any other query parameter automatically prefills the field with a matching `id`.

## 6. YAML Schema Reference

### Top-level fields

| Field | Required | Description |
|---|---|---|
| `version` | Yes | Always `1` |
| `title` | No | Form title. Supports localization (`Record<string, string>`). |
| `description` | No | Optional subtitle. Supports localization. |
| `sections` | Yes | Array of section objects. |
| `connections` | No | Array of integration objects (webhook, email, Airtable). |
| `completion` | No | Custom completion screen configuration. |
| `start_date` | No | ISO date string. Form shows "not yet open" before this date. |
| `end_date` | No | ISO date string. Form shows "closed" after this date. |
| `locale` | No | Default locale code (e.g. `en`, `es`). Overridden by `?lang=`. |
| `mixpanel` | No | Mixpanel project token for event analytics. |

### Section fields

| Field | Description |
|---|---|
| `id` | Unique identifier for the section. |
| `title` | Section heading. Supports localization. |
| `fields` | Array of field objects. |
| `next` | Navigation target: a section `id`, `"done"`, a URL, or a conditional array. |

**Conditional `next` syntax:**
```yaml
next:
  - when: data.question_1 == "Yes"
    go: section_2
  - else: done
```

### Field fields

| Field | Description |
|---|---|
| `id` | Unique identifier. Used in expressions and prefill. |
| `type` | Field type (see Section 7). |
| `label` | Field label. Supports localization. |
| `placeholder` | Input placeholder text. Supports localization. |
| `validators` | Array of validator rules (see Section 8). |
| `options` | Array of option strings or `{value, label}` objects. For selection types. |
| `visible_when` | Expression string. Field is shown only when the expression evaluates to true. |
| `otp` | Boolean. On `email` fields, triggers OTP verification before proceeding. |
| `searchable` | Boolean. On `dropdown` fields, enables search/filter input. |
| `outputFormat` | `"structured"` on `address` fields returns a structured address object. |
| `min_label` | Label for the low end of a `rating` scale. |
| `max_label` | Label for the high end of a `rating` scale. |

## 7. Field Types

18 field types are supported.

**Text input**
- `short_text` — single-line text input
- `long_text` — multi-line textarea
- `email` — email address input with format validation
- `url` — URL input with format validation
- `number` — numeric input
- `mobile_number` — phone number input with international format

**Selection**
- `single_select` — choose one from a list of options (radio/button style)
- `multiple_select` — choose one or more from a list of options
- `dropdown` — single selection via dropdown; supports `searchable: true`

**Specialized**
- `date` — date picker
- `rating` — numeric scale with optional `min_label` / `max_label`
- `signature` — freehand signature capture
- `file_upload` — file attachment
- `hidden` — not shown to respondent; populated via URL prefill

**Address**
- `address` — full address input; supports `outputFormat: structured`
- `address_locality` — city or locality input
- `address_region` — state or region input
- `address_country` — country input

### OTP verification

Set `otp: true` on an `email` field to require verification before the respondent proceeds.

- Code length: 6 digits
- Code expiry: 10 minutes
- Resend cooldown: 30 seconds
- Maximum attempts: 5

```yaml
- id: email
  type: email
  label: Email address
  otp: true
  validators:
    - required
```

## 8. Validators

Validators are defined as an array on any field.

**`required`** — field must have a value before proceeding.
```yaml
validators:
  - required
```

**`pattern`** — value must match a regular expression.
```yaml
validators:
  - type: pattern
    regex: "^[a-zA-Z0-9_]+$"
    message: Only letters, numbers, and underscores are allowed
```

**`min`** — minimum value (numeric) or minimum length (text).
```yaml
validators:
  - type: min
    value: 3
```

**`max`** — maximum value (numeric) or maximum length (text).
```yaml
validators:
  - type: max
    value: 20
```

`message` is optional on `pattern`, `min`, and `max`. Supports localization.

## 9. Connections / Integrations

Connections are defined under the top-level `connections` array. Three types are supported.

### Webhook

Posts the full submission JSON to a URL on every submission event, including partial submissions.

```yaml
connections:
  - type: webhook
    url: https://example.com/webhook
```

### Email (via Resend)

Sends an email on completed submissions only.

```yaml
connections:
  - type: email
    to: "{{data.question_2}}"
    subject: "New submission - {{form.title}}"
    body: "<p>Hi {{data.question_1}}, we received your response.</p>"
    include_responses: true
```

- `to`, `subject`, and `body` support Handlebars templating. Available context: `data` (field values keyed by field `id`) and `form` (form metadata including `title`).
- `include_responses: true` appends an HTML table of all field responses to the email body.
- Multiple email connections can be defined (e.g. one to the team, one confirmation to the respondent).

### Airtable

Creates a new record in an Airtable base on completed submissions only.

```yaml
connections:
  - type: airtable
    connection_id: 1ymdt3kpmquv9p8527hf1t4h
    base_id: appuxoklE4VlF1kqN
    table_id_or_name: Leads
```

- Requires an OAuth connection established via the platform, stored server-side and referenced by `connection_id`.
- Pass `?connection_id=<value>` in the form URL to associate the form with a specific stored connection.

## 10. Advanced Features

### Conditional navigation

Route respondents to different sections based on their answers. Define `next` as an array of condition objects.

```yaml
next:
  - when: data.question_1 == "Yes"
    go: section_2
  - else: done
```

### Conditional visibility

Show or hide fields based on the values of other fields. The `visible_when` expression has access to the `data` object.

```yaml
- id: passport_number
  type: short_text
  label: Passport Number
  visible_when: data.citizenship === 'No'
```

### Prefill via URL

Any query parameter not reserved by the platform prefills the field whose `id` matches the parameter name.

```
https://app.declarativeforms.com/acme/forms/onboarding?name=Jane&email=jane@example.com
```

Fields with `id: name` and `id: email` will be pre-populated.

### Form gating

Control form availability by date.

```yaml
start_date: 2025-01-01T00:00:00.000Z
end_date: 2025-12-31T23:59:59.999Z
```

Visitors outside the date range see an appropriate message ("not yet open" or "closed").

### Localization

String fields (`title`, `description`, `label`, `placeholder`, `message`) accept either a plain string or a locale map:

```yaml
title:
  en: Customer Feedback
  es: Opinión del cliente
```

- Set `locale` at the top level to specify the default.
- Respondents can override with `?lang=es` in the URL.

### Custom completion screen

```yaml
completion:
  title: "Thank you, {{data.question_1}}!"
  message: We've received your application and will be in touch within 48 hours.
  button:
    label: Visit our website
    url: https://example.com
```

`title` and `message` support Handlebars templating with `data` context. All fields support localization.

### Mixpanel analytics

Set `mixpanel` to a project token to track form events.

```yaml
mixpanel: fffd6fab3138c0c0af6609cd986ece5e
```

### Partial submissions and resume

Submission progress is saved between steps. The `submission_id` is tracked in the URL. To resume an in-progress form, pass both `?submission_id=<id>` and `?step=<section_id>`.

## 11. Canonical Example

`rental.yaml` — a rental application form. Used as the reference example throughout all documentation. All guides build incrementally on this form.

```yaml
version: 1
title: Rental Application
sections:
  - id: basic_info
    title: Basic info
    fields:
      - id: full_name
        type: short_text
        label: Full name
        validators:
          - required
      - id: email
        type: email
        label: Email address
        validators:
          - required
      - id: unit_type
        type: single_select
        label: Unit type
        options:
          - Studio
          - 1 bedroom
          - 2 bedrooms
        validators:
          - required
    next: done
```

Field IDs: `full_name`, `email`, `unit_type`. Single section: `basic_info`.

## 12. Tone and Voice

- Pain-first: lead with the problem, not the feature.
- No unverifiable adjectives: avoid "seamless", "easy", "simple", "powerful".
- Concrete and specific: show the YAML, show the URL, show the mechanism.
- Each instruction starts with a verb.
- Short sentences. No hedging.

## 13. Support Model

All support is handled via GitHub Issues: `https://github.com/declarativeforms/.github/issues`

- Response target: 24 hours on all issues.
- Feature requests that genuinely improve the product: 48-hour shipping promise.
- Bug reports should include: form URL, expected behavior, actual behavior, steps to reproduce, browser and OS, relevant YAML snippet.

---

## 14. Business Model and Pricing

Currently free. No account required. No sign-up gate.

Form hosting requires only a public GitHub repository. There are no usage limits documented at this time.

Note: paid tiers or support for private repositories may be introduced in future.
