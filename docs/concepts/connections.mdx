---
title: Connections
---

Connections define what should happen after a submission is received. Use them to deliver submission data to external destinations such as email, webhooks, or Airtable.

## Overview

Connections are defined in the form-level `connections` array. Each connection type has its own configuration shape because each destination works differently, so this page documents each supported type separately.

## `email`

Use an email connection when a submission should trigger a confirmation or notification email.

### Structure

```yaml
type: email
to: "{{data.question_1}}"
subject: "Thanks for your submission"
body: |
  Hi {{data.question_1}}, we received your response.
include_responses: true
```

### Fields

<ParamField path="type" type="email" required>
  Defines the connection as an email delivery.
</ParamField>

<ParamField path="to" type="string" required>
  Defines the recipient email address.
</ParamField>

<ParamField path="subject" type="string | object" required>
  Defines the subject line of the email.
</ParamField>

<ParamField path="body" type="string | object">
  Defines the body content of the email.
</ParamField>

<ParamField path="include_responses" type="boolean">
  Defines whether form responses are included in the email.
</ParamField>

### Details

Email connections are useful for confirmation emails or simple post-submit notifications.

The `subject` and `body` fields support localized text. In the examples used across the docs, the email content can also reference submission data with templates.

## `webhook`

Use a webhook connection when a submission should be forwarded to another system or custom backend.

### Structure

```yaml
type: webhook
url: "https://example.com/webhook"
```

### Fields

<ParamField path="type" type="webhook" required>
  Defines the connection as a webhook delivery.
</ParamField>

<ParamField path="url" type="string" required>
  Defines the URL that receives the submission.
</ParamField>

### Details

Webhook connections are the simplest integration shape because they only require a destination URL.

Use them when submission data should be forwarded to another system outside Declarative Forms.

## `airtable`

Use an Airtable connection when submissions should be delivered into an Airtable base.

### Structure

```yaml
type: airtable
connection_id: "conn_123"
base_id: "app123"
table_id_or_name: "Responses"
```

### Fields

<ParamField path="type" type="airtable" required>
  Defines the connection as an Airtable delivery.
</ParamField>

<ParamField path="connection_id" type="string" required>
  Defines the Airtable connection ID used to authenticate the delivery.
</ParamField>

<ParamField path="base_id" type="string" required>
  Defines the Airtable base where submissions are delivered.
</ParamField>

<ParamField path="table_id_or_name" type="string" required>
  Defines the Airtable table where submissions are delivered.
</ParamField>

### Details

Airtable connections depend on a previously created connection ID.

To obtain one in the hosted app, open `https://app.declarativeforms.com/oauth/airtable`. This starts the Airtable OAuth flow. After setup completes, the app redirects to `/connections?id=<connection_id>`, where the connection ID is shown so it can be copied into the form configuration.

Once you have the connection ID, `base_id` and `table_id_or_name` define where submissions should be delivered inside Airtable.
