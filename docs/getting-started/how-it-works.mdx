---
title: How it works
description: What happens when you push a YAML file and visit the form URL.
---

There are four things worth understanding about how the platform works. This page covers each one, using `feedback.yaml` as the example.

---

## 1. Where the YAML comes from

When you push `feedback.yaml` to your repository's `main` branch, it becomes accessible at:

```
https://raw.githubusercontent.com/{owner}/{repo}/main/feedback.yaml
```

When someone visits `https://app.declarativeforms.com/{owner}/{repo}/feedback`, the API fetches that raw URL, parses the YAML, and returns a JSON representation to the browser. The form always reflects the current `main` branch.

---

## 2. How the form renders

The browser receives the parsed form definition and renders the first section. For `feedback.yaml`, that means two `short_text` fields: `name` and `message`.

Field values stay in the browser until the user submits. Validation (if configured) runs client-side before each submission.

---

## 3. How submissions work

When the user submits a section, the browser sends the field values to the API. The API saves a submission record and returns a `submission_id`. On the final section, the submission is marked `completed` and any configured connections fire.

For `feedback.yaml` — a single-section form — there is no intermediate step. Submit the section, and it's done.

---

## 4. Partial saves

For multi-section forms, the submission ID and current step are written into the URL after each section:

```
https://app.declarativeforms.com/{owner}/{repo}/feedback?submission_id=abc123&step=next_section
```

This URL can be bookmarked or shared. When revisited, the browser resumes from the saved step with previously entered data pre-populated.

`feedback.yaml` has only one section, so this doesn't apply yet — but it will once you add a second section in [Sections and navigation](/concepts/sections-and-navigation).
