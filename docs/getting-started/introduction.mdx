Declarative Forms turns a YAML file in a public GitHub repository into a live hosted form.

`https://app.declarativeforms.com/{owner}/{repo}/{form_name}`

No builder UI. No account. No setup flow.

---

## Why this exists

AI tools can generate infrastructure, tests, and app scaffolding, but forms still usually require clicking through a builder. That breaks code-first workflows.

Declarative Forms keeps forms in the same system as the rest of your product:

- Text-based definitions
- Version history in Git
- Pull request review and diffs
- Easy generation with Claude Code, Codex, and similar tools

---

## How it works

1. Write a YAML file (`version: 1`)
2. Push it to a public GitHub repository
3. Open `https://app.declarativeforms.com/{owner}/{repo}/{form_name}`

If your file is `intake.yaml`, your form URL ends with `/intake`.

---

## Where it fits

- Internal tools and operational workflows
- Customer intake and onboarding
- Hiring and application collection
- AI-assisted build flows where forms are generated from prompts

---

## Example patterns

### Hiring intake

```yaml
version: 1
title: Candidate Screening
sections:
  - id: candidate
    fields:
      - id: full_name
        type: short_text
        label: Full name
        validators:
          - required
      - id: role
        type: single_select
        label: Role
        options:
          - Backend Engineer
          - Product Designer
          - Product Manager
    next: done
```

### Customer onboarding

```yaml
version: 1
title: New Customer Intake
sections:
  - id: onboarding
    fields:
      - id: company_name
        type: short_text
        label: Company name
        validators:
          - required
      - id: team_size
        type: dropdown
        label: Team size
        options:
          - 1-10
          - 11-50
          - 51-200
          - 201+
      - id: use_case
        type: long_text
        label: What are you trying to solve?
    next: done
```

### Internal operations request

```yaml
version: 1
title: Operations Request
sections:
  - id: request
    fields:
      - id: request_type
        type: single_select
        label: Request type
        options:
          - Access
          - Procurement
          - Incident
      - id: priority
        type: single_select
        label: Priority
        options:
          - Low
          - Medium
          - High
      - id: details
        type: long_text
        label: Details
        validators:
          - required
    next: done
```

All three are published with the same URL pattern:
`https://app.declarativeforms.com/{owner}/{repo}/{form_name}`

---

## Why teams choose it over builders

**Code-native changes.** Form updates are commits you can diff and review.

**AI-compatible workflow.** Prompt an AI tool, get YAML, and commit. No manual rebuild in a separate UI.

**No signup gate.** A public GitHub repository is enough to publish.

---

## What to know before using it

- The repository must be public for hosted rendering.
- Declarative Forms is strongest when your team already works in Git.
- If you need a drag-and-drop visual builder as your source of truth, this may not be the best fit.
